# Compile FP16 by signed INT4 GEMM on CUDA

This example compiles and runs `A[M, K] @ B[N, K].T` for FP16 activations and signed four-bit weights on a CUDA GPU. The compiler stores two weights per byte, dequantizes each K tile during the kernel, and accumulates in FP32 before writing FP16 output.

## Use the API

Create an `int8` tensor with values in `[-8, 7]`. The packer pads an odd K dimension with zero and returns contiguous `uint8` bytes. To run the public consumer from the checkout root without importing TileLang's unbuilt source tree, invoke the example by its full script path:

```powershell
& $python examples\dequantize_gemm\p21_quickstart.py
```

The script imports `p21_fp16xint4` beside itself, asserts TileLang 0.1.15 came from the installed environment rather than this checkout, and runs a small odd-K GEMM against an independent CUDA FP32 reference. For embedding the API in another application, import `pack_signed_int4` and `fp16xint4_gemm` from `p21_fp16xint4` after installing TileLang v0.1.15 and adding the example directory through the consumer's normal packaging configuration.

`packed_weights` has shape `[N, ceil(K/2)]`. The lower K index uses the low nibble. The upper K index uses the high nibble. Two's-complement nibbles represent values from -8 through 7.

## How the schedule chooses a plan

The schedule uses 128 threads per block, 64 K values when possible, and 16 or 64 M rows based on the input height. It chooses 64 or 128 N columns based on the output width. Three pipeline stages are used when K has at least three full tiles. Shorter reductions use two stages.

The schedule estimates decoded fragment values per thread. At 32 or fewer values, it leaves decoded weights in the fragment. Above 32, it copies them to a swizzled shared-memory tile when the estimated staged tile fits the device shared-memory limit. The estimate uses logical tile bytes. The CUDA compiler can add padding or change lifetimes, so the generated code and measured resource use remain the final check.

`placement="fragment"` and `placement="shared"` select a plan for controlled comparisons. `placement="auto"` applies the hardware-aware policy. The two forced paths compile the same logical input and output contract.

This P21 example currently enforces the active SM120 CUDA device as its target. Use `fp16xint4_gemm` with tensors on the current device. The returned schedule is specialized for the current device, and this initial API does not promise multi-GPU dispatch.

## Exact accumulation

`fp16xint4_gemm(A, packed_B, accumulation="exact")` selects a separate scalar kernel. The same trailing argument is available on `compile_fp16xint4`; its compiled call remains `kernel(A, packed_B, C)`. The default is `accumulation="fp32"`, which retains the tensor-core schedule. Exact mode requires `placement="auto"` because it decodes one scalar weight per iteration rather than using either staged tile layout. The returned plan names the accumulation mode and reports its actual one-dimensional 128-thread schedule with no shared-memory staging.

Every finite FP16 value is an integer multiple of 2^-24. The exact kernel scales each activation by 2^24, multiplies its integer representation by the signed INT4 value, and adds into signed int64. The maximum product magnitude is `65504 * 2^24 * 8`; bounding K to 1,049,088 prevents overflow for every intermediate sum. Finite sums that can round to finite FP16 fit exactly in FP64. CUDA `__double2half` rounds the final scaled sum directly, avoiding the FP32 intermediate used by a generic CUTLASS double-to-half cast. Values beyond FP16 range overflow to the appropriate infinity. Nonfinite products accumulate separately on-device, preserving NaN, infinity-times-zero and opposing-infinity behavior. NaN payload bits and negative-zero payload identity are not promised.

The path has no decoded dense weights, data-dependent workspace or host readback. Its scalar work scales with M*N*K, so it is an accuracy option rather than a claim of tensor-core throughput. The [measured report](../../docs/evidence/P21/exact-20261024/results.md) keeps its correctness and cost separate from earlier fast-mode measurements.

## Verify the real kernels

Use the commands and isolated environment in the project-local [verification skill](../../.agents/skills/verify-low-precision-tensor-compiler/SKILL.md). Drive runs the upstream fallback and checks small odd-tail, rectangular odd-tail, and medium GEMMs against CPU float64 and CUDA float32 references. It also checks exact signed, cancellation, and zero outputs while poisoning the unused high nibble for odd K. It saves TileLang TIR and generated CUDA source for each schedule.

Benchmark compares the selected kernel with Torch unpack plus dense matmul and forced fragment/shared placement controls at the same medium shape. It warms all paths, excludes compilation, rotates four-way side order over seven samples, and verifies every final result. It reports host wall-clock operation latency (including public API and allocation overhead) separately from CUDA event time on the stream (enqueued GPU work). The Torch baseline includes unpack work but is not a low-bit vendor library. Report the measured result for the tested GPU and shapes; do not infer performance on another GPU.

## What this example reuses

The application and compiler are TileLang v0.1.15. The kernel uses its Python TIR frontend, `T.Pipelined`, `T.alloc_fragment`, `T.alloc_shared`, layout inference, and `T.gemm`. The upstream repository's dequantization GEMM example already stages decoded values through fragments and shared memory.

P21 adds the signed FP16 by INT4 GEMM entry point, the compile-time fragment-versus-swizzled-shared placement policy, and its CUDA verification and benchmark driver. The policy is a bounded extension inspired by the storage-type and layout conversion choices in Ladder. It does not reproduce Ladder's full search or compiler passes.

The [CMU FP16xINT4 course report](https://www.andrew.cmu.edu/user/zhiboc/15745-fa24/final_report.pdf) describes an independent TVM implementation with tiling, register dequantization, warp layout, pipelining, and parameter search. This example does not copy that report's source or claim its results.

Ladder's type and layout transformations are described in [the OSDI 2024 paper](https://www.usenix.org/system/files/osdi24-wang-lei.pdf). P21 implements only the compile-time decode placement and tile policy described here.
